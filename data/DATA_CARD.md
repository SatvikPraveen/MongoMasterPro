# Data Card: MongoMasterPro Learning-Platform Dataset

This document follows the structure proposed in *Datasheets for Datasets*
(Gebru et al., 2021) so that anyone using the dataset for a benchmark or a
course can see exactly how it was produced and where its limits are.

| Field | Value |
|-------|-------|
| Dataset name | `mongomasterpro-learning-platform` |
| Schema version | 1.0 |
| Generator | `data/generators/generate_data.py` v2.0.0 |
| Default seed | `20251003` |
| Default reference date | `2025-01-01T00:00:00Z` |
| Output format | MongoDB Extended JSON v2 (canonical), JSON Lines, one file per collection |
| Target database | `learning_platform` |
| Licence | MIT (same as the repository); all content is synthetic |

## 1. Motivation

The dataset exists so that every learning module, validation script and
benchmark in MongoMasterPro runs against the **same, citable data**. It models
a small online-learning business (users, instructors, courses, enrollments,
reviews, click-stream events), which exercises the document-model decisions
that matter in practice: embedding versus referencing, denormalised counters,
unique compound keys, time-series style events and text search.

It is *not* a sample of any real platform. No record describes a real person.

## 2. Composition

Seven collections are produced. Counts below are the `lite` and `full` targets;
`--scale` multiplies all of them (minimum one document per collection).

| Collection | lite | full | Key fields | Referential links |
|------------|-----:|-----:|------------|-------------------|
| `categories` | 20 | 50 | `name` (unique), `level`, `parent_id`, `course_count` | `parent_id` → `categories._id` |
| `users` | 1 000 | 10 000 | `email` (unique), `username` (unique), `profile`, `preferences`, `status` | — |
| `instructors` | 50 | 200 | as `users` plus `instructor_stats` | — |
| `courses` | 100 | 1 000 | `title`, `instructor_id`, `category`, `category_id`, `difficulty_level`, `price`, `content.modules`, `enrollment_count`, `rating`, `status` | `instructor_id` → `instructors._id`; `category_id` → `categories._id` |
| `enrollments` | 5 000 | 50 000 | `(user_id, course_id)` unique, `progress`, `completion_status`, `completion_date`, `enrolled_at` | `user_id` → `users._id`; `course_id` → `courses._id` |
| `reviews` | ≤1 500 | ≤15 000 | `rating` (1–5), `title`, `comment`, `helpful_votes` | `user_id`, `course_id`, `enrollment_id` |
| `analytics_events` | 10 000 | 100 000 | `event_type`, `session_id`, `properties`, `timestamp` | `user_id`; `course_id` for course-scoped events |

Field names are `snake_case` and types are exactly those demanded by the JSON
Schema validators that `docker/init/00_bootstrap.js` attaches to each
collection (ObjectId references, BSON dates, 32-bit integers for counters).

### Distributions worth knowing about

* **User status**: 85 % active, 10 % inactive, 5 % suspended.
* **Course status**: 10 % draft, 85 % published, 5 % archived.
* **Completion status**: 10 % not started, 40 % in progress, 30 % completed, 20 % dropped.
* **Review ratings** are skewed positive: completed courses draw from {3,4,5} with weights 0.1/0.3/0.6; in-progress courses from {2,3,4,5} with 0.1/0.2/0.4/0.3. Reviews are only written by users with an in-progress or completed enrollment.
* **Event mix**: course_view 30 %, login 15 %, quiz_attempt 12 %, logout 10 %, enrollment 10 %, video_play 10 %, completion 8 %, download 5 %. Events span the 90 days before the reference date and are emitted in timestamp order.
* **Enrollment pairs** are sampled *uniformly without replacement* from the user × course product, so popularity is flat; there is no long tail of popular courses. Experiments on skewed access patterns must impose skew themselves.
* **Timestamps** are uniform within their windows (users: 730 days before the reference date; courses: 540 days; events: 90 days). There is no weekly or seasonal periodicity.

### Derived fields

After generation the following counters are recomputed from the referencing
documents so the dataset is internally consistent: `courses.enrollment_count`,
`courses.rating.{average,count}`, `categories.course_count`,
`instructors.instructor_stats.{total_courses,total_students,total_revenue,average_rating}`.

### Identifiers

`_id` values are ObjectIds whose leading four bytes encode the document's own
creation timestamp (the remaining eight bytes come from the seeded RNG). They
therefore behave like production ObjectIds for insertion-order and locality
experiments, while remaining fully reproducible.

## 3. Collection process

Everything is generated by `generate_data.py`. All randomness is drawn from one
`random.Random(seed)` instance and a `Faker` instance seeded with the same
value; nothing reads the clock or the process id. Timestamps are generated
relative to the reference date. With pinned library versions
(`data/generators/requirements.txt`) a given parameter set reproduces
byte-identical files; `tests/python/test_generate_data.py` enforces this.

Names, free text, user agents and IP addresses come from Faker's `en_US`
providers. Password hashes have the shape of bcrypt hashes but are random
strings, not hashes of any password.

## 4. Preprocessing and output

No preprocessing is applied after generation. Files are written as canonical
Extended JSON so that type information survives a round trip through
`mongoimport`; `--import` loads the same in-memory documents through PyMongo.
Import removes existing documents with `delete_many` (not `drop`) so the
validators and indexes created by the bootstrap are preserved.

`manifest.json` records parameters, library versions, per-collection record
counts and SHA-256 digests. `checksums.sha256` is in `sha256sum -c` format.

## 5. Recommended uses

* Teaching material for the modules under `scripts/`.
* Baseline data for the experiments under `experiments/`, which cite the
  manifest's seed and digests in their results.
* Schema-validation and index-design exercises.

## 6. Limitations and known biases

* Synthetic text is lorem-ipsum-like English; text-search relevance results are
  not meaningful beyond demonstrating the mechanics.
* Access patterns are uniform, so cache-hit and hot-key behaviour is more
  benign than in real systems.
* There is a single locale and a small set of time zones and languages.
* Instructors are stored in a separate collection with no validator; the lab
  modules model instructors as a role on `users` instead. Both patterns are
  deliberately present for comparison.
* The dataset is small by production standards; `full` is about 176 000
  documents. Scale up with `--scale` for storage-engine experiments.

## 7. Maintenance and versioning

Changes to field names, enums or distributions must bump `SCHEMA_VERSION`;
changes that alter output for the same parameters must bump
`GENERATOR_VERSION`, and both must be noted in `CHANGELOG.md`. Results produced
by the experiment harness embed the manifest, so old results remain
interpretable after a bump.
